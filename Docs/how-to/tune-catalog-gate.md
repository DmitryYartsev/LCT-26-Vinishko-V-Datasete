# Настройка решения «вино есть в каталоге»

## Как принимается решение

По одному сходству первого кандидата сервис не может отличить «это оно» от «похожая этикетка
другого вина», поэтому решение принимается в три шага:

| Условие | Результат | `gate_reason` |
|---|---|---|
| сходство `top1 ≥ thresh_score` (верхний порог) | карточка сразу | `visual_hi` |
| `top1 < thresh_score_lo` (нижний порог) | «вина в каталоге нет» | `low_score` |
| между порогами | карточка только если модель уверенно подтвердила кандидата | `ocr_confirms`, `ocr_agrees` |
| между порогами, подтверждения нет | «вина в каталоге нет» | `ocr_not_confirmed` |

Подтверждением считается одно из двух:

* модель переставила ответ на этого кандидата и уверена в нём не меньше `ocr.confirm_confidence`;
* модель согласилась с кандидатом поиска с уверенностью не меньше `csv_match.agree_confidence`.

## Когда менять

| Симптом | Что делать |
|---|---|
| у вин, которых нет в каталоге, слишком часто появляется карточка | поднять `thresh_score` или пороги подтверждения |
| у настоящих каталожных вин слишком часто «вина нет в каталоге» | опустить `thresh_score` и/или `thresh_score_lo`, ослабить пороги подтверждения |
| решения выглядят случайными в середине диапазона | проверить, включено ли чтение этикетки и есть ли ключ (`ocr.enabled`, `/health → api_key`) |

## Шаг 1. Подготовить два набора

* **позитивы** — фотографии вин, которые в каталоге есть (например `data/real_photo`);
* **негативы** — фотографии вин, которых в каталоге нет (`data/negatives`, а лучше — свой сток).

## Шаг 2. Прогнать и посмотреть решения

```bash
for f in data/negatives/*; do
  printf '%s\t' "$(basename "$f")"
  curl -s -F "image=@$f" http://localhost:8080/v1/search \
    | python3 -c "import json,sys; d=json.load(sys.stdin); \
      print(d['in_catalog'], d['gate_reason'], round(d['confidence']['top1_score'], 4))"
done
```

Аналогично по позитивам. Считайте три числа: сколько негативов получили карточку (ложные карточки),
сколько позитивов потеряли карточку и сколько ответов оказалось неверными.

## Шаг 3. Поменять пороги

`config/pipeline.yaml`, секция `retrieval` и связанные пороги:

```yaml
retrieval:
  thresh_score: 0.81        # верхний порог: карточка сразу
  thresh_score_lo: 0.70     # нижний порог: ниже — «нет в каталоге»
ocr:
  confirm_confidence: 0.80  # уверенность, с которой модель подтверждает карточку
csv_match:
  agree_confidence: 0.80    # уверенность «модель согласна с поиском»
```

Затем:

```bash
docker compose restart ml
```

## Шаг 4. Проверить, что стало лучше

Повторите шаг 2 и сравните с прежними числами. Меняйте по одному параметру за раз: пороги связаны,
и сдвиг двух сразу не даёт понять, что именно помогло.

## О чём помнить

* Пороги калибровались на небольшом числе вин вне каталога, поэтому на вашем стоке их стоит
  перепроверить: ложная карточка заметнее для пользователя, чем «нет в каталоге».
* Если чтение этикетки выключено (`ocr.enabled: false`) или ключ не задан, средний диапазон
  всегда превращается в «нет в каталоге» — решение работает как два обычных порога.
* Верхний порог влияет на самое заметное поведение: он решает, показывать ли карточку без всякой
  проверки текстом.
* Значения `thresh_*` попадают и в ответ `/v1/search` (`confidence.thresholds`), так что по логам
  видно, на каких порогах принималось решение.
