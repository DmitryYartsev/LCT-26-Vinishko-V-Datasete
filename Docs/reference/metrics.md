# Справочник: метрики качества

## Как сравнивается ответ с истиной

Для каждого фото в манифесте указан правильный slug каталога. Ответ считается верным в одной
из двух семантик:

| Семантика | Правило |
|---|---|
| **точное совпадение** | slug ответа в точности равен slug из манифеста |
| **«то же вино»** | совпадает всё, кроме года и крепости: они записаны хвостовым числом в slug |

Семантика «то же вино»: ответ считается верным и тогда, когда отличается год или крепость —
то есть вино того же наименования другого года засчитывается как правильный ответ. Например
`…-bryut-115` и `…-bryut-125` — одно вино, а `…-beloe-suhoe-12` и `…-beloe-polusladkoe-12` —
разные (различаются сахаром).

Правило реализуется сравнением слагов без хвостового числа (год или крепость):

```python
import re
trail = re.compile(r'-\d+(?:[.,]\d+)?$')

def same_wine(a: str, b: str) -> bool:
    """То же ли это вино: год/крепость (хвостовое число слага) не важны."""
    if not a or not b:
        return False
    base = lambda s: trail.sub('', s.strip().lower())
    return a == b or base(a) == base(b)
```

## Проценты (accuracy)

**Accuracy — это recall@1**: доля фото, у которых первый ответ совпал с истиной. Отдельной
метрики не считается.

## Recall@k

| Метрика | Смысл |
|---|---|
| `recall@k` визуального поиска | правильный slug попал в первые `k` кандидатов поиска (k = 1, 5, 10, 30) |
| `recall@k` с чтением этикетки | ответ модели ставится первым, дальше идёт пул поиска без него — и правильный slug ищется в первых `k` такой последовательности |

Прирост `recall@k` после чтения этикетки показывает, что модель успевает «вытащить» правильное
вино даже тогда, когда визуальный поиск поставил его не первым.

## Precision@k и F1@k

На одно фото приходится один правильный ответ, поэтому:

* `precision@k = hits / (n · k)` — доля правильных среди всех показанных позиций;
* `F1@k = 2·P·R / (P + R)`, где `R` — recall@k.

Следствия, о которых стоит помнить, читая таблицы: `precision@1 = recall@1`, а `precision@k` и
`F1@k` быстро падают с ростом `k` просто потому, что в списке всегда только один правильный
элемент. Сравнивать `precision@k` и `F1@k` корректно только между вариантами в одной строке.

## Как устроены данные для оценки

Форматов два, и их легко перепутать: один используется для прогона скриптом, второй — для подсчёта
метрик.

### 1. Набор для прогона скриптом: папка фотографий + TSV-манифест

Так устроена папка `eval/` в репозитории, и так же выглядит любой набор, который вы готовите сами
(см. [../tutorials/first-evaluation.md](../tutorials/first-evaluation.md)):

```
мой-набор/
├── queries/                 # фотографии, имена произвольные
│   ├── 019c68d0.jpg
│   └── 096ca74e.jpg
└── queries.tsv              # манифест: две колонки, разделитель — символ табуляции
```

```
query_id	image_path
q-000001	019c68d0.jpg
q-000002	096ca74e.jpg
```

* первая колонка — идентификатор запроса (попадает в результат как `query_id`);
* вторая — путь к фотографии **относительно папки с фотографиями**;
* первая строка — заголовок `query_id<TAB>image_path`; скрипт проверяет его при запуске.

Формат именно TSV, потому что манифест читает `eval/participant_test.sh`: он разбирает строки
по табуляции, считает контрольную сумму каждой фотографии и пишет `predictions.jsonl`. В наборе
`eval/` дополнительно лежат `checksums.sha256` (контрольные суммы фотографий) и `README.md`.

Этот формат рассчитан на случай, когда правильные ответы неизвестны тому, кто запускает прогон:
скрипт сохраняет только предсказания, а сопоставление с истиной делает тот, кто оценивает.

### 2. Манифесты с истиной: CSV в `data/`

Наборы для измерения качества лежат в `data/` — это CSV с колонками `image,true_slug`: имя файла
фотографии и правильный slug каталога.

| Манифест | Фотографий | Где лежат сами файлы |
|---|---|---|
| `data/eval62.csv` | 62 | `data/real_photo/` |
| `data/eval233_rest.csv` | 171 | `data/eval/` |
| `data/eval2.csv` | 105 | `data/eval2_images/` |

Формат другой, потому что метрике нужна истина. Фотографии могут лежать как плоским списком
(`real_photo`, `eval2_images`), так и в папках по винам (`data/eval2/<slug>/`) — в манифесте
в любом случае указано имя файла.

Для сравнения моделей наборы объединяются: 62 + 171 + 105 = 338 фотографий. Затем из объединённого
набора исключаются фотографии со спорной разметкой — те, где независимые источники (визуальный
поиск и разные модели чтения этикетки) устойчиво называют другое вино. Для итоговых замеров
остаётся 300 фотографий.

### 3. Фотографии вин вне каталога

Отдельный каталог `data/negatives/` — фотографии вин, которых в каталоге нет. Он нужен для проверки
решения «вина в каталоге нет»: на нём видно, сколько раз сервис всё-таки показал карточку.

Набор небольшой и перед использованием проверяется вручную: часть фотографий может оказаться вином
из каталога другого года. Такие фотографии исключаются — для калибровки порогов остаются только
действительно отсутствующие в каталоге вина (8 из 11).

## Метрики решения «вино есть в каталоге»

Отдельно измеряется само решение показывать карточку или сценарий «похожие вина»:

| Величина | Как считается |
|---|---|
| ложная карточка | фото вина, которого нет в каталоге, получило карточку каталожного вина |
| точность карточек | доля верных ответов среди фото, где карточку показали |
| сохранённые карточки | сколько верных ответов не потеряли карточку из-за строгости порогов |

Эти величины считаются на фотографиях вин вне каталога (`data/negatives/`) и на позитивных
наборах, и напрямую связаны с порогами из `reference/configuration.md`.
