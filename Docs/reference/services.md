# Справочник: сервисы, порты и тома

Всё поднимается одним `docker compose up` из корня репозитория. Ниже — фактическая картина того,
что запускается, в каком порядке и на каких портах.

## Сервисы

| Сервис | Образ / сборка | Порт на хосте | Роль |
|---|---|---|---|
| `db` | `pgvector/pgvector:pg16` | не публикуется | Postgres + pgvector: карточки (`wines`), векторы (`wine_vectors`), профили сомелье (`wine_profiles`) |
| `fetch` | `python:3.11-slim` | — | одноразовый: проверяет и докачивает `data/`, `filtered/`, `models/`, дамп индекса |
| `db-init` | `pgvector/pgvector:pg16` | — | одноразовый: если база пустая — восстанавливает дамп, иначе выходит |
| `ml` | сборка `./ML service` | **8080** | распознавание: визуальный поиск + OCR-переранжирование |
| `sommelier` | сборка `./sommelier service` | **8090** | диалог (LLM), голос (STT), скоринг «вино ↔ цель», аналоги |
| `web` | сборка `./web` (Nuxt/Nitro) | **3000** | UI + BFF-роуты `/api/*` |
| `https` | `caddy:2-alpine` | **80**, **443** (`HTTP_PORT`/`HTTPS_PORT`) | HTTPS перед `web`: без него браузер не даёт микрофон |
| `eval` | `alpine:3.20` + bash/curl/jq (профиль `eval`) | — | прогон набора фотографий против `ml` внутри сети |

Порядок запуска (кто кого ждёт):

```
fetch ──► db-init ──► ml ─────┐
   │        │                 ├──► web ──► https
   └────────┴──► db ──► sommelier ──┘
```

* `ml` стартует только после `db` (healthy), `db-init` и `fetch` (completed) — так исключена
  гонка «сервис принимает запросы, пока индекс ещё строится».
* `web` объявлен как `depends_on: [ml, sommelier]` **без** `condition: service_healthy`:
  контейнер поднимается сразу, как только соседи созданы. Если сканировать сразу после
  «первого» `up`, `ml` может ещё прогреваться — дождитесь `healthy` (`docker compose ps`).
* `eval` ждёт `ml` в состоянии healthy — прогон всегда стартует по готовому сервису.

## Тома

| Том | Что внутри | Терять можно? |
|---|---|---|
| `pgdata` | все данные Postgres, в том числе **векторы индекса** | нет: потеря = пересборка индекса (~40 мин на 8 ядрах, дольше на слабых машинах) |
| `hfcache` | кэш HuggingFace для `ml` | да, качается заново |
| `caddydata` | сертификаты и внутренний CA Caddy | да, но браузер начнёт ругаться заново |

Смонтированные папки репозитория (важно понимать, что меняется без пересборки):

| Куда | Откуда | Режим |
|---|---|---|
| `/app/ml` | `./ML service` | rw — код `ml` читается с хоста, перезапуск `ml` подхватывает правки |
| `/app/config` | `./config` | ro — конфиг пайплайна, источник истины |
| `/app/ref` | `./data` | ro — манифесты, эталонные фото, OCR-разметка каталога |
| `/app/filtered` | `./filtered` | ro — фото каталога и `catalog.csv` |
| `/app/models` | `./models` | rw — веса энкодеров и детекторов |
| `./paths.py` | `./paths.py` | ro |
| `/models_cache` | том `hfcache` | rw |

## Healthcheck'и и что смотреть

| Сервис | Проверка | Период |
|---|---|---|
| `db` | `pg_isready -U vino` | 5 с, 20 попыток |
| `ml` | GET `/health` (uvicorn слушает только после прогрева) | 10 с, 6 попыток, `start_period: 60m` — запас на сборку индекса с нуля |
| `sommelier`, `web`, `https` | нет | проверяйте HTTP-запросом |

Быстрая диагностика:

```bash
docker compose ps                                   # кто поднялся и кто healthy
docker compose logs -f ml                           # прогрев, OCR, ошибки
docker compose stats --no-stream                    # CPU/RAM по контейнерам
curl -s localhost:8080/health                       # модель, индекс, число вин, OCR
curl -s localhost:8090/health
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/
docker compose logs db-init | tail -5               # восстановился ли дамп индекса
```

## Ресурсы

Практический минимум, проверенный на реальном стенде:

| Ресурс | Хватает | Комментарий |
|---|---|---|
| CPU | 4 ядра | один скан с OCR ≈ 6–20 с; OCR-вызов идёт по сети, CPU почти не занимает |
| RAM | 8 ГБ минимум, 16 ГБ с запасом | стек в покое ≈ 1 ГБ; пик — сборка индекса |
| Диск | 30 ГБ минимум | модели ≈ 1.4 ГБ, данные ≈ 0.4 ГБ, образы ≈ 3 ГБ + `pgdata` |
